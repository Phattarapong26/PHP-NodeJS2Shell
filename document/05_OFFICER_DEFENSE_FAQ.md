# 05. แนวทางการตอบข้อซักถามเชิงเทคนิค (Technical Defense Guide)
**คู่มือชี้แจงและตอบข้อซักถามสำหรับนำเสนอผู้เชี่ยวชาญ / ผู้บังคับบัญชา**

---

## 🎯 วัตถุประสงค์ของเอกสารนี้
เอกสารฉบับนี้จัดทำขึ้นเพื่อเตรียมความพร้อมในการชี้แจงเชิงเทคนิค (Oral Technical Defense) เมื่อต้องนำเสนอผลงานต่อผู้บังคับบัญชา, กรรมการตรวจรับงาน, หรือนายทหารฝ่ายเทคโนโลยีสารสนเทศ (เช่น ยศเรือโท หรือผู้เชี่ยวชาญไซเบอร์) โดยครอบคลุมคำถามดักคอและคำถามเชิงลึกทั้งหมด พร้อมคำตอบที่มีหลักการและอ้างอิงโค้ดประกอบชัดเจน

---

### คำถามที่ 1: "คุณใช้ AI ช่วยเขียน แล้วคุณเข้าใจระบบข้างในจริงไหม? อธิบายซิว่าระบบส่งแพ็กเก็ตตั้งแต่ต้นจนจบอย่างไร?"

**แนวทางการตอบแบบมืออาชีพ (Clear & Confident):**
> *"เข้าใจอย่างถ่องแท้ในทุกเลเยอร์ครับ สถาปัตยกรรมของ OPScaner ทำงานประสานกัน 4 ขั้นตอนอย่างชัดเจนครับ:*
> 1. *ขั้นแรก (L1/L2 Discovery): เมื่อสั่งสแกน Subnet โมดูล `core/multi_vector_discovery.py` จะใช้กลไก Async Semaphore ยิงตรวจสอบ 5 เวกเตอร์พร้อมกัน ได้แก่ TCP Core Handshake, UDP NetBIOS (พอร์ต 137), mDNS (พอร์ต 5353), Gateway DHCP PTR, และ Host ARP Table ทำให้ค้นพบอุปกรณ์ที่เปิดโหมด Stealth หรือไม่ตอบรับ Ping ได้ครบถ้วน*
> 2. *ขั้นที่สอง (L4 Port & Banner): ส่งการเชื่อมต่อไปยังพอร์ตบริการ เพื่อวัดค่า Latency แท้จริง และดึง Server Banner พร้อมค่า IP TTL เพื่อใช้จำแนกตระกูลระบบปฏิบัติการ (TTL 64 = Linux, TTL 128 = Windows)*
> 3. *ขั้นที่สาม (L7 & Precondition): โมดูล `audit/precondition_prober.py` และ `audit/kernel_audit.py` จะตรวจสอบเงื่อนไขจำเป็นทางสถาปัตยกรรม เช่น ตรวจว่า NGINX มี alias+rewrite หรือไม่ และทดสอบ Socket MPTCP (Protocol 262) เพื่อดูว่ามีเวกเตอร์ช่องโหว่เคอร์เนลหรือไม่*
> 4. *ขั้นสุดท้าย (Classification & Synthesis): โมดูล `audit/nginx_audit.py` จะบังคับใช้ OS Boundary Gating คัดกรองไม่ให้ช่องโหว่ข้ามระบบปฏิบัติการ และส่งต่อไปยัง `reports/amber_builder.py` เพื่อสร้างรายงาน PDF TLP:AMBER พร้อมกล่องคำสั่ง Host-Check ให้ผู้ดูแลระบบครับ"*

### คำถามที่ 2: "ทำไมเราไม่ใช้ Nmap หรือ Nessus ที่เป็นมาตรฐานสากลอยู่แล้ว? ทำเครื่องมือนี้ขึ้นมาทำไม?"

**แนวทางการตอบ (Focus on Operational Limitations):**
> *"มีเหตุผลทางยุทธวิธีและข้อจำกัดของเครื่องมือดั้งเดิม 3 ประการสำคัญครับ:*
> 1. *ข้อจำกัดด้านสภาพแวดล้อม Container: หากเรานำ Nmap หรือ Nessus ไปรันใน Docker หรือสภาพแวดล้อมที่จำกัดสิทธิ์ (Non-root) Nmap จะติดปัญหา Virtual Bridge NAT ไม่สามารถทำ Raw ARP Scan ข้ามวงแลนได้ ทำให้สแกนไม่พบโฮสต์ แต่ OPScaner ถูกออกแบบระบบ Multi-Vector มาเพื่อแก้ปัญหานี้โดยเฉพาะ*
> 2. *ความเสี่ยงการถูกไฟร์วอลล์บล็อก (Stealth Operation): Nmap หรือ Nessus มักยิงกวาดพอร์ตมหาศาล (Aggressive Sweep) ซึ่งจะไปกระตุกระบบ IDS/IPS หรือไฟร์วอลล์ของหน่วยงานจนถูกตัดการเชื่อมต่อทันที แต่ OPScaner ใช้ระบบ Targeted Precondition Probing ซึ่งส่งแพ็กเก็ตน้อยกว่า 90% แต่ได้ข้อมูลสถาปัตยกรรมที่แม่นยำกว่า*
> 3. *ความสอดคล้องกับมาตรฐานไทย (ThaiCERT Compliance): เครื่องมือต่างประเทศไม่จัดกลุ่มสินทรัพย์ตามเกณฑ์ สกมช. 8 กลุ่ม และไม่สามารถสร้างรายงานภาษาไทยตามมาตรฐาน TLP:AMBER ที่มีฟอนต์ราชการ (TH Sarabun) ฝังในตัวได้เหมือนระบบนี้ครับ"*

### คำถามที่ 3: "เราสแกนผ่านเครือข่าย Subnet ภายนอก คุณรู้ได้อย่างไรว่าเครื่องมีช่องโหว่ Linux Kernel CVE-2026-98432? คุณเจาะเข้าไปในเครื่องเขาได้จริงหรือมโนขึ้นมา?"

**แนวทางการตอบ (Honest, Technical & High Rigor):**
> *"เรียนตามตรงในหลักการเครือข่ายครับว่า สแกนเนอร์ที่สแกนจากภายนอก **ไม่มีทางและไม่ควรส่งคำสั่ง Shell เข้าไปเจาะระบบโดยพลการ** เพราะนั่นเป็นการกระทำที่ผิดกฎหมายและอาจทำให้เซิร์ฟเวอร์ปลายทางล่ม (Denial of Service)*
> 
> *ดังนั้น สิ่งที่ OPScaner ทำ จึงแบ่งออกเป็น 2 ส่วนตามหลักสากล:*
> 1. *การตรวจจับทางเครือข่าย (Remote Network Probe): ระบบทดสอบการตอบรับของพอร์ตว่ามีการเจรจาโปรโตคอล MPTCP (MultiPath TCP) หรือไม่ ซึ่งเป็นเวกเตอร์ที่เปิดทางให้เกิดช่องโหว่ Use-After-Free ของเคอร์เนลดังกล่าว*
> 2. *การกำหนดระดับความเชื่อมั่นเป็น `Conditional` (มีเงื่อนไข): เรา **ไม่ได้เคลมว่าเจาะระบบสำเร็จ** แต่เราออกคำแนะนำเฝ้าระวัง พร้อมสร้างกล่องคำสั่ง **Host-Check Checklist** มาตรฐาน:*
>    ```bash
>    cat /etc/os-release && uname -r && ps aux | grep -iE 'falcon|sentinel|wazuh|edr|defender'
>    ```
>    *เพื่อให้ผู้ดูแลระบบนำชุดคำสั่งนี้ไปรันตรวจสอบเวอร์ชันเคอร์เนลจริงภายในเครื่อง นี่คือมาตรฐานการรายงานที่โปร่งใสและถูกต้องตามหลักวิศวกรรมความมั่นคงปลอดภัยครับ"*

---

### คำถามที่ 4: "ทำไมในรายงานต้องระบุว่า 'กรณีใช้ Docker หรือ Kubernetes ให้ตรวจสอบเครื่อง Host/Node ด้วย'?"

**แนวทางการตอบ (Architecture Insight):**
> *"เพราะสถาปัตยกรรมของ Container บนระบบ Linux เป็นแบบ **Shared Kernel Architecture** ครับ ต่างจาก Virtual Machine (VM) ทั่วไป:*
> * ตัว Container ไม่ได้จำลองเคอร์เนลของตัวเอง แต่เรียกใช้เคอร์เนลร่วมกับเครื่องแม่ข่าย (Host / Worker Node) เสมอ*
> * เมื่อรันคำสั่ง `uname -r` ภายในคอนเทนเนอร์ ค่าที่ได้คือเวอร์ชันเคอร์เนลของเครื่อง Host แม่ข่ายจริง*
> * หาก Linux Kernel ของ Host มีช่องโหว่ในระดับเน็ตเวิร์ก (เช่น CVE-2026-98432) จะส่งผลกระทบต่อทุกคอนเทนเนอร์ที่รันอยู่บนโหนดนั้นทั้งหมด จึงต้องแจ้งเตือนให้ผู้ดูแลระบบตรวจสอบไปถึงระดับ Host Node ครับ"*

---

### คำถามที่ 5: "รอบที่แล้วมีคนทำรายงานหลุดจุดโป๊ะ เอาช่องโหว่ Windows CVE-2024-4577 ไปใส่บน CentOS (Linux) ระบบของคุณป้องกันความผิดพลาดแบบนี้อย่างไร?"

**แนวทางการตอบ (Showcase of OS Boundary Gating):**
> *"จุดนี้เป็นจุดชูโรงของระบบเราเลยครับ เราพัฒนาโมดูลที่ชื่อว่า **OS Boundary Gating** ขึ้นมาใน `audit/nginx_audit.py` และ `audit/kernel_audit.py`:*
> * ระบบจะทำ Passive OS Fingerprinting ผ่านค่า IP TTL และ Server Tokens ก่อนเสมอ*
> * หากตรวจพบว่าเป็น Linux (TTL 64 / Apache CentOS / Ubuntu) ระบบจะ **บล็อกและคัดกรองช่องโหว่เฉพาะของ Windows (เช่น CVE-2024-4577 หรือ IIS vulnerabilities) ทิ้งไป 100%***
> * และหากตรวจพบว่าเป็น Windows (TTL 128 / IIS) ระบบจะ **ตัดช่องโหว่ Linux Kernel ทิ้งทันที** เช่นกัน*
> * รวมถึงการแยกประเภทช่องโหว่ระหว่าง Direct Command Injection บนไฟล์ .aspx (CWE-78) กับ PHP CGI Argument Injection ออกจากกันอย่างเด็ดขาด ทำให้รายงานของเรามีความสอดคล้องทางเทคนิค (Coherent) และไม่มีจุดโป๊ะเรื่อง Tech Stack Mismatch แน่นอนครับ"*
