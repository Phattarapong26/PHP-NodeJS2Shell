AsyncIO Concurrency: 120 TCP Timeout: 0.15s Max Batch: 512 hosts
PHASE 0

การจัดเตรียมสภาพแวดล้อมและการรัน (Orchestration & File Setup)

ไฟล์ที่ทำงาน: run.sh, docker-compose.yml, Dockerfile

Offline POSIX UDP
1. แก้ไขปัญหา Directory Mount

ตรวจสอบและลบไดเรกทอรีผิดพลาดหาก Docker เคยสร้างทับ แล้ว touch host_network.json เป็นไฟล์จริงก่อน container สตาร์ท

2. ตรวจสอบการ์ดเครือข่ายจริง

ตัดการ์ดเสมือน (docker0, br-*, veth*, tun*) ทิ้ง คัดเลือกเฉพาะการ์ดจริงผ่าน route -n get default หรือ ip route

3. Offline Socket Probe

เชื่อมต่อ UDP Socket ไปยัง Gateway IP โดยไม่ยิงแพ็กเก็ตออกอินเทอร์เน็ต ได้ IP จริงของเครื่องใน 0.0001 วินาที แม้ระบบอยู่ในเครือข่ายปิด (Air-gapped)

PHASE 1

ระบบตรวจจับเครือข่ายอัตโนมัติ (Dynamic Subnet Ingestion)

ฟังก์ชัน: my_ip_route(), get_host_network_info() ใน app.py:575

TTL 60s Cache
1. HTTP Host Header Fallback

เมื่อผู้ใช้เปิดเบราว์เซอร์เข้าผ่าน IP (เช่น http://192.168.1.41:5050) ระบบอ่านค่าจาก request.host ทันที แก้ปัญหา Docker IP หลอก

2. Docker Bridge Elimination

ปฏิเสธ IP ในช่วง 172.16.0.0/12 ของ Docker Container ไม่ให้นำมาเป็นวง LAN ขององค์กรโดยเด็ดขาด

3. Class C Safe Slicing

หากเครือข่ายเป็น /16 หรือ /22 ระบบจะตัดวงเฉพาะกลุ่มเครื่องท้องถิ่น (/24 ขนาด 254 เครื่อง) เป็นค่าเริ่มต้น ไม่ให้เผลอสแกน 65,534 เครื่อง

PHASE 2

กระจายงานคู่ขนานความเร็วสูง (High-Concurrency Async Dispatcher)

ฟังก์ชัน: scan(), parse_target_hosts() ใน app.py:2429

Async Semaphore (120)
1. Subnet & Port Matrix

สร้าง Matrix เป้าหมาย 254 โฮสต์ x 12 พอร์ตมาตรฐาน = 3,048 งาน หรือกำหนดพอร์ตเป้าหมายเฉพาะเจาะจง

2. Zero-Subprocess Architecture

ส่งค่า curr_host_ip, curr_is_docker เข้าไปใน Loop ล่วงหน้า ห้ามเรียก subprocess.run ใน Loop พอร์ตปิดเด็ดขาด แก้ปัญหาค้าง 100%

3. AbortController Support

เชื่อมต่อสัญญาณยกเลิกจากฝั่ง Web UI ผู้ใช้กดปุ่ม 'หยุดสแกน' เพื่อตัด HTTP Request และคืนทรัพยากรทันทีในเสี้ยววินาที

PHASE 3

การตรวจสอบพอร์ตแบบไม่บล็อก (Pre-flight TCP Check & Hairpin Fallback)

ฟังก์ชัน: check_tcp_port() ใน app.py:1688

0.15s Non-blocking Handshake
1. Fast TCP SYN Check

ส่ง TCP Handshake ด้วย Timeout 0.15s (ปกติพอร์ตเปิดตอบใน 1-5 ms) หากพอร์ตปิด OS คืนค่า RST ทันที ไม่เสียเวลารอ

2. Safe Socket Cleanup

ครอบคำสั่ง writer.wait_closed() ด้วย timeout 0.05s ป้องกันเธรดค้างกรณีเซิร์ฟเวอร์ปลายทางไม่ส่ง FIN/ACK

3. Docker NAT Hairpin Bypass

หากเป้าหมายคือเครื่อง Host ตัวเอง (127.0.0.1 หรือ IP เครื่อง) สลับเชื่อมต่อไปยัง Docker Gateway หรือ host.docker.internal อัตโนมัติ

PHASE 4

การจำแนกเทคโนโลยีและลายเซ็น (Deep Fingerprint & Signature Matching)

ฟังก์ชัน: probe_endpoint() ใน app.py:1700-1850

Zero Weaponized Payload
1. Header Analysis

วิเคราะห์ Server, X-Powered-By, X-Node-Version, ตรวจสอบ Brotli ผ่าน Content-Encoding: br

2. Session Cookies

ตรวจจับ PHPSESSID, ci_session, laravel_session, connect.sid, koa.sess

3. DOM & Body Markers

ตรวจจับ wp-content, phpmyadmin, __next_data__, /_nuxt/, @vite/client

4. Secondary Probes

ตรวจสอบ /index.php และ Easter Egg ?=PHPB8B5F2A0... เพื่อยืนยัน PHP แม้เซิร์ฟเวอร์จะซ่อน header

PHASE 5

การประเมินกลไกความเสี่ยง 5 สาย (5 Security Chains Audit: Chains A ถึง E)

ฟังก์ชัน: audit_security_chains(), probe_lfi_prerequisite() ใน app.py:1570-1685

Terminal Explainer Layout
Chain A: Upload Progress

ตรวจการเปิดฟีเจอร์อัปโหลดไฟล์แฝงใน Session ซึ่งเป็นจุดเริ่มการสร้างโค้ดแฝง

Chain B: Info Exposure

ตรวจการเปิดเผยหมายเลขเวอร์ชัน PHP และ OS ผ่าน expose_php / Server Header

Chain C: Deserialization

ตรวจความเสี่ยงจากการสลับ serialize_handler ข้ามรูปแบบ (php vs php_serialize)

Chain D: Memory Limit

ตรวจความเสี่ยง OOM Bailout และขอบเขตหน่วยความจำใน Zend Engine

Chain E: Worker Lifecycle

ตรวจการคงค้างของบัฟเฟอร์ใน PHP-FPM Worker ที่ไม่ถูกรีไซเคิล (pm.max_requests)

การตรวจสอบ LFI แบบปลอดภัย (Benign Canary Probe): ทดสอบส่ง canary token เช่น ?page=thaicert_audit_probe_canary_test เพื่อดูข้อผิดพลาด include stream โดยไม่มีการรันคำสั่ง OS หรือทิ้งไฟล์อันตรายใดๆ บนเครื่องเป้าหมาย
PHASE 6

ผสานข้อมูล Layer 2 ARP และจัดกลุ่มตาม ThaiCERT 8 มิติ

ฟังก์ชัน: get_live_lan_hosts(), resolve_device_details() ใน app.py:2514-2598

Layer 2 ARP Mapping

ดึงข้อมูล MAC Address จาก ARP Table จัดกลุ่มอุปกรณ์ที่ไม่มีพอร์ตเว็บ เช่น ปรินเตอร์, เราเตอร์, กล้องวงจรปิด ไม่ให้หลุดจากการตรวจสอบ

2. ThaiCERT 8 Groups Summary

คำนวณและจัดสรรอุปกรณ์เข้า 8 หมวดหมู่ (CMS, Mobile API, Control Panel, IoT, Docker, Windows PHP, Dev/Legacy, Outsourced)

3. Real-time Dashboard Rendering

ส่งผลลัพธ์ JSON กลับไปยัง Frontend พร้อมค่า Latency รายเครื่อง และเปิดให้คลิกตรวจสอบ Deep Audit รายพอร์ตได้ทันที

ขอบเขตการทำงานของระบบ (Scope of Audit & Detection)

ระบบถูกออกแบบมาเพื่อเป็น เครื่องมือตรวจประเมินความปลอดภัยเชิงรับ (Non-destructive Security Audit Tool) ประจำหน่วยงานและองค์กร ครอบคลุมทั้งระบบเครือข่ายและเว็บแอปพลิเคชัน

1. รูปแบบเป้าหมายที่รองรับ (Target Formats)

  • CIDR Subnet (Class C & Enterprise):

    รองรับ 192.168.1.0/24, 10.0.0.0/22, 172.16.0.0/24 โดยมีระบบจำกัดขนาดเพื่อความปลอดภัย (Max Scan 512 hosts)

  • Single Host IP (/32):

    ระบุตรวจสอบเครื่องเดี่ยว เช่น 192.168.1.41 หรือ 10.10.20.15/32

  • IP Range:

    ระบุช่วง IP เริ่มต้นถึงสิ้นสุด เช่น 192.168.1.10 - 192.168.1.50

  • Domain & FQDN:

    ใส่ชื่อโฮสต์ เช่น intranet.org.go.th ระบบทำการ Resolve DNS อัตโนมัติ

  • Port Specific Target:

    รองรับการระบุพอร์ตในเป้าหมาย เช่น 192.168.1.41:8080 หรือ dev.local:3000

2. พอร์ตบริการที่ตรวจสอบ (Ports In-Scope)

ระบบตรวจสอบพอร์ตบริการเว็บและแอปพลิเคชันมาตรฐาน 12 พอร์ตที่นิยมใช้รัน PHP, Node.js, Reverse Proxy และ Dev Server:

80 (HTTP) 443 (HTTPS) 8080 (Alt-HTTP/Proxy) 8000 (Dev Server) 8888 (Webmin/PHP) 8081 (Docker/Node) 8443 (Alt-HTTPS) 3000 (Node.js/Next.js) 5000 (Flask/Express) 5050 (Scanner/App) 4000 (Backend API) 5173 (Vite/SPA)

💡 ผู้ดูแลระบบสามารถกำหนดพอร์ตเอง (Custom Ports) ได้อย่างอิสระตั้งแต่พอร์ต 1 ถึง 65535 ในหน้าตั้งค่า

3. ขอบเขตการจัดกลุ่มสินทรัพย์สารสนเทศตาม ThaiCERT 8 มิติ (Asset Classification)

กลุ่ม 1: เว็บไซต์และระบบภายในองค์กร

CMS: WordPress, Joomla, Drupal, Intranet Portal ภายในหน่วยงาน

กลุ่ม 2: ระบบหลังบ้านแอปมือถือ และ API

Mobile API, REST/JSON Endpoints, Node.js / Express / Next.js SSR

กลุ่ม 3: Hosting Control Panel

แผงควบคุมโฮสติ้ง cPanel, DirectAdmin, Plesk, Webmin (พอร์ต 8888, 8080)

กลุ่ม 4: ซอฟต์แวร์และอุปกรณ์สำเร็จรูป

อุปกรณ์เครือข่าย, กล้อง CCTV, เครื่องพิมพ์ Network Printer ผ่าน Layer 2 ARP

กลุ่ม 5: Container และ Docker Image

ระบบที่รันบน Docker, Alpine Linux, คอนเทนเนอร์ไมโครเซอร์วิส

กลุ่ม 6: Windows ที่มี PHP ติดตั้งอยู่

Microsoft IIS, XAMPP on Windows, PHP-CGI (เสี่ยงต่อ CVE-2024-4577)

กลุ่ม 7: ระบบทดสอบ ระบบเก่า และสำรอง

Staging/Dev Server, PHP 5.6/7.4 เก่าที่ไม่ได้แพตช์, เครื่องลืมปิด

กลุ่ม 8: ระบบที่ผู้ให้บริการภายนอกดูแล

Outsourced Web Application, Vendor Managed Services, SaaS ภายนอก

ข้อจำกัดเชิงเทคนิคและสภาพแวดล้อม (Technical Limitations & Boundaries)

ความโปร่งใสในขอบเขตการทำงาน สิ่งที่ระบบทำได้และข้อจำกัดที่ไม่สามารถตรวจได้จากเครือข่ายภายนอก (เพื่อความเข้าใจที่ถูกต้องของผู้ตรวจสอบ)

1. ขอบเขตความปลอดภัย (Non-destructive Design)

ระบบปฏิเสธการส่ง Payload เจาะระบบจริง (Exploitation) หรือรันคำสั่ง OS เช่น shell_exec('id') หรือการเขียน Shell ลงดิสก์อัตโนมัติทั้งวง LAN:

เหตุผล: เพื่อป้องกันไม่ให้ Memory Corruption (Use-After-Free) ไปทำลายกระบวนการทำงานของ PHP-FPM / Apache จนเซิร์ฟเวอร์โรงพยาบาลหรือธนาคารเกิด Service Crash และป้องกันไม่ให้เกิดความผิดตาม พ.ร.บ. คอมพิวเตอร์ฯ

2. ข้อจำกัดเรื่อง VLAN และ Client Isolation

การตรวจจับอุปกรณ์รอบข้างผ่าน Layer 2 ARP จะทำงานได้สมบูรณ์ใน Broadcast Domain เดียวกัน:

ผลกระทบ: หากเครือข่ายองค์กรมีการเปิดใช้ Client Isolation บน Wi-Fi หรือเครื่องสแกนเนอร์อยู่คนละ VLAN ผ่านเราเตอร์ L3 การค้นหาเครื่องที่ไม่มีพอร์ตเว็บผ่าน ARP อาจไม่เห็นอุปกรณ์บางส่วน

3. การซ่อนเวอร์ชัน (Header Hardening)

กรณีที่เซิร์ฟเวอร์เป้าหมายปิดการแสดงผล expose_php = Off และปรับแก้ Server Token ให้เป็นชื่ออื่น:

ผลกระทบ: ระบบจะใช้การวิเคราะห์พฤติกรรม (Behavioral Signatures, Cookies, Framework Markers) ซึ่งอาจระบุเวอร์ชันได้เป็นช่วงความเสี่ยง แทนที่จะเป็นเลข Patch ย่อยที่แน่นอน

4. เพดานการสแกนเครือข่ายขนาดใหญ่ (Max Scan Cap)

ระบบกำหนดเพดาน max_scan = 512 hosts เพื่อความปลอดภัยของโครงข่ายองค์กร:

ผลกระทบ: หากผู้ใช้กรอก Subnet ขนาดมหาศาล เช่น 10.0.0.0/8 หรือ 172.16.0.0/16 ระบบจะตัดสแกนเฉพาะช่วง Class C แรก (254 เครื่อง) เพื่อไม่ให้ทราฟฟิกถล่ม Core Switch ขององค์กร
